# 视频生成器真实业务录制可靠性产品思考

## 用户问题

真实业务录制失败不是单纯的 selector 问题。昨天原纸贸易订单录入暴露了更基础的流程风险：原始脚本被覆盖、旁白被过度润色、业务测试数据被替换、hover 菜单无法表达、远程下拉无法操作、上传合同文件缺失、手动录制丢失 segment 时间轴，最后把长旁白压进短视频导致语速异常。

这类问题如果等到 TTS、录屏和 ffmpeg 合成后才发现，返工成本很高，而且容易误用错误成片。因此需要把“能不能录”前置到正式生成之前。

## 为什么先做 preflight dry-run

Preflight dry-run 的目标不是生成素材，而是回答几个录制前问题：

- 脚本是否能解析。
- 登录态文件是否存在。
- 需要上传的文件是否准备好。
- 页面动作是否能在浏览器中执行。
- 失败时有没有截图、候选元素和失败 segment 可诊断。

这让用户可以先修脚本、登录态和前置资料，再决定是否生成 TTS 和视频。代价是多了一条命令，但它能避免生成无用音频和错误成片。

## 为什么做脚本三稿

原始脚本是用户意图的证据，不能被 agent 直接覆盖。润色稿和可执行稿承担不同职责：

- 原始稿保留用户输入。
- 润色稿调整旁白和节奏。
- 可执行稿补充选择器、上传文件路径和特殊动作。

三稿机制的价值是让“表达优化”和“执行适配”可追溯。尤其是客户名“测试”这类业务数据，失败时应先排查控件和环境，而不是直接替换数据。

## 为什么新增显式动作语法

真实业务系统常见控件不能都用普通点击和输入表达：

- 左侧菜单需要 hover 才显示二级菜单。
- Element UI remote select 需要点击、键盘输入、等待远程选项、选择第一项。
- 地址等下拉常常只需要“选第一个”。
- 合同生成流程需要上传本地文件。

把这些模式显式写成 `悬停`、`远程选择`、`选择 ... 第一个`、`上传文件`，比让 agent 隐式猜测更稳定，也更容易在 preflight 中诊断失败。

## 为什么报告要脱敏

录制脚本和真实页面可能包含客户名、合同文件名、本地用户目录、密码或 token。失败报告需要足够可诊断，但不能把用户输入值、远程选择关键字和上传文件路径持久化写出。

因此报告保留 segment、action 类型、截图路径和候选元素结构信息；输入值和文件路径用脱敏动作替代。截图仍可能包含页面可见业务信息，所以它是本地诊断产物，不应对外分发。

## 体验取舍

- `--prepare-script` 与 `--dry-run` 互斥：避免用户以为一次命令既生成三稿又完成 preflight。
- `uploadFile` 在 dry-run 中只检查文件存在，不实际上传：减少业务副作用。
- 下拉候选只在可见 dropdown/listbox 内查找：牺牲一点宽松匹配，换取不点错无关列表项。
- 原始稿冲突直接失败：让用户显式处理原始脚本差异，避免静默覆盖。

## 适用场景

- 真实业务网页教程录制。
- 需要登录态和菜单导航的操作路径。
- 需要远程下拉、选择第一项、上传附件的表单流程。
- 需要先确认前置资料，再生成 TTS 和视频的录制任务。

## 已知局限

- 这次 P0 只解决 dry-run、三稿和新动作语法；半自动 custom handler 保留 segment 时间轴仍在后续 Phase 4。
- dry-run 不执行真实上传，因此无法证明上传后的业务校验一定通过。
- 失败截图可能包含页面可见业务数据，需要作为本地产物谨慎处理。
- 远程选择只覆盖常见 Element UI / dropdown 模式，特殊组件仍可能需要 custom handler。

## 后续方向

- 继续规范化 debug attempt 和最终素材目录，避免多次试跑产物散落。
