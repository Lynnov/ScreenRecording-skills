# 原纸贸易订单录入录制复盘（2026-05-29）

## 背景

本次目标是把原纸贸易订单录入脚本真正录成一条可交付视频，最终产物为 `video-runs/原纸贸易-订单录入-final/final.mp4`。

相较于上一轮复盘，这一次的重点不是重做方案，而是把已经可用的录制链路稳定跑通，并尽量减少首页导航、菜单 hover、选择器歧义和上传路径这些高频失败点。

## 最终结果

- 直达订单录入页的 dry-run 通过。
- 正式生成成功，最终视频路径：`video-runs/原纸贸易-订单录入-final/final.mp4`。
- `run-report.json` 为 `ok: true`。
- 视频时长约 `120.18s`。

## 这次最有效的改动

### 1. 直接从订单录入页开始

首页“开启工作” + 左侧菜单 hover 在 dry-run 和正式录制里表现不一致，正式录制尤其容易因为鼠标停留时间、cursor overlay、hover 状态回收而失败。

最终改成直接打开：

`https://intelligenttest.cpsol.net/microFront/djrawpaper_trade/#/orderManage/orderEntry`

这是最有效的降风险手段。相比首页导航，它减少了一个完整的 UI 状态机，也省掉了额外的旁白停顿和鼠标轨迹变量。

### 2. 把容易歧义的文本都换成精确 selector

这次主要踩坑都来自“文本看起来对，但页面里不止一个同名元素”的问题：

- “开启工作”不是按钮，是 `div.index-left-button`。
- “原纸贸易” 在多个区域里都可能出现。
- “订单录入” 既有列表页标题，也有侧边栏二级菜单。
- “自提价” 在页面里重复出现很多次。
- “请输入客户名称/手机号” 在页面里也不止一个。

最后稳定下来的方式是：

- 首页入口用 `.index-left-button`
- 菜单入口用 `.collect-menu-all-system-item:has-text("原纸贸易")`
- 二级菜单用 `.waterfall-item-child:has-text("订单录入")`
- 价格类型等待用 `input[value="pick_up"]`
- 订单列表页等待用 `input[placeholder="请输入客户名称/手机号"] >> nth=0`
- 商品表单字段用 `.el-dialog:visible ... >> nth=0/1`

这比继续堆语义匹配更可靠。

### 3. 远程搜索和下拉选择需要处理 Element UI 的真实行为

客户名称和收货地址都是 Element UI 风格的远程选择控件，实际行为和普通 `fill()` / `click()` 不一样。

这次修了三件事：

- `remoteSelect` 输入需要等待 `readonly` 解除，再输入；否则会把查询字符吞掉。
- 下拉列表里可能先出现隐藏的容器或空容器，不能只看第一个 `dropdown`。
- 选择完下拉项后要等待下拉关闭，不然后续字段会被残留 popper 干扰。

这些修复都已经进入 `src/lib/video-generator/browser/interaction-rules.ts`，并有对应单测。

### 4. 正式录制和 dry-run 的差异要单独看

这次一个很重要的经验是：`dry-run` 通过不代表正式录制一定能过。

原因有两个：

- 正式录制里有 cursor overlay 和真实视频录制上下文，actionability 更敏感。
- 旁白与等待时间会影响 hover / dropdown 的存活时间，特别是菜单这种“hover 后一会儿就收起”的 UI。

所以这次最终用了“把页面状态变量压缩到最少”的策略：

- 首页直接跳过
- 菜单动作合并到同一段
- 复杂字段用精确 selector
- 上传文件改成绝对路径

## 失败点和对应修复

### 首页点击失败

现象：正式录制里 `click text=开启工作` 超时。

根因：页面上的“开启工作”并不是标准 button，而是一个可点击 `div`，text click 在正式录制上下文里不稳定。

修复：改成 `.index-left-button` 精确 selector，并且后面菜单动作尽量合并到同一段。

### 二级菜单 hover 不稳定

现象：`原纸贸易` / `订单录入` 在正式录制里有时找不到，或者 hover 后菜单收起。

根因：hover 菜单对时间敏感，旁白停顿会影响菜单可见状态。

修复：

- 用精确 selector 定位菜单项。
- 把“开启工作 -> hover -> 点击二级菜单”压到同一段脚本里。
- 最终再进一步绕过首页，直接进订单录入页。

### 上传文件路径错误

现象：`uploadFile` 解析成了不存在的 `E:\视频脚本原稿\...`。

根因：相对路径层级写多了，script parser 会按脚本文件目录去解析。

修复：最终改成绝对路径：

`E:/Code/ScreenRecording/视频脚本原稿/原纸贸易-订单录入-生成订单.png`

### 录制结束等待条件歧义

现象：脚本最后等“订单详情”，但订单提交后页面实际回到订单列表。

根因：结束后的真实页面状态和文案不一致，而且 `订单详情` 文本本身不稳定。

修复：把最后的等待改成订单列表页真实 selector，避免无意义失败。

## 下次可以继续优化的点

### 1. 给正式录制做“页面阶段别名”

这次脚本大量依赖具体 UI 文本，但正式录制时真正稳定的是“页面阶段”，不是文案。

这个步骤最好前移到脚本润色阶段，但不要改动原始业务脚本。推荐继续保留“三稿”结构：原始稿只保留业务人员写法；润色稿整理旁白、顺序和节奏；可执行稿再补 `stage` 别名、稳定等待点、弹窗 scope、上传文件绝对路径等录制信息。

可以考虑把常见页面阶段抽象成：

- 首页
- 模块列表页
- 订单录入列表页
- 订单弹窗

命名时按“业务模块 + 页面/状态”组织，例如：

- `module.rawpaperTrade`：原纸贸易模块上下文。
- `orderEntry.list`：订单录入列表页，用 URL 片段和列表页锚点识别。
- `orderEntry.createDialog`：新增订单弹窗，用 `.el-dialog:visible` 这类可见容器 scope，加标题和关键字段锚点识别。
- `orderEntry.goodsDialog`：商品或明细弹窗，同样用可见弹窗容器和字段锚点识别。

独立页面可以用 URL 区分，弹窗不能依赖 URL，应该把它当成 scoped stage：先确认可见弹窗容器存在，再把后续 selector 限定在这个容器里找，避免撞到列表页、隐藏弹窗或其他重复字段。

脚本层面可以变成：

```md
@stage orderEntry.list
打开订单录入页
点击「新增」

@stage orderEntry.createDialog
选择客户名称「测试客户」
选择收货地址「测试地址」
上传合同图片「E:/Code/ScreenRecording/视频脚本原稿/xxx.png」
点击「生成订单」

@stage orderEntry.list
等待回到订单列表
```

然后每个阶段用一个更稳定的锚点 selector，而不是直接写业务文案。这样 dry-run 和正式录制失败时，报告可以先说明“没有进入 `orderEntry.createDialog`”，再展示缺失锚点或重复候选，而不是只报某个 selector timeout。

### 2. 给录制器加“可见但不可 actionability”的诊断

这次很多失败都不是“找不到元素”，而是：

- 元素可见但没展开
- 元素存在但被遮挡
- 元素存在但真实下拉没加载完
- dry-run 能通过，但正式录制因为 `recordVideo`、cursor overlay、页面动画或接口响应变慢而失败

后续不建议一遇到 Playwright 找不到元素就改成坐标点击或图像识别。更稳的方向是：Playwright 继续负责真实操作，但失败时自动生成“现场诊断包”，先判断根因到底是页面慢、selector 歧义、弹窗未进入、元素被遮挡，还是录制模式开销导致 actionability 条件迟迟不满足。

诊断包可以包含：

- 当前 URL 和当前 `stage` 名称。
- 失败 action、原始 selector、解析后的 selector。
- 候选元素数量，以及每个候选的 `visible`、`enabled`、尺寸、文本摘要。
- 当前可见弹窗数量、命中的弹窗 scope、隐藏弹窗数量。
- dropdown / popper 容器数量，哪些为空、哪些隐藏、哪些可见。
- `document.elementFromPoint()` 结果，用来判断目标点是否被遮挡。
- 失败瞬间截图、必要时保存 DOM 片段或可见文本摘要。
- 最近请求是否还有 pending，辅助判断是不是接口慢或远程下拉没加载完。

如果预检或失败报告能直接标出这些信息，就能把 `locator.click timeout` 拆成更可行动的诊断结论，例如：

- `orderEntry.createDialog` 没有命中：说明还没进入新增订单弹窗。
- selector 命中 4 个候选：说明脚本需要收紧 scope 或改成 stage 内查找。
- 目标元素可见但 `elementFromPoint` 是遮罩层：说明被弹窗、loading 或残留 dropdown 遮挡。
- dropdown 容器存在但可见项为空：说明远程搜索还没返回，不应该立即点击。
- dry-run 正常但正式录制失败：优先检查录制模式下页面响应、动画和 overlay 对 actionability 的影响。

这样做的价值不是绕开 Playwright，而是用 Playwright 和浏览器运行时信息解释“为什么按顺序能操作的脚本，在自动录制时失败”。

### 3. 首页导航如果还要保留，最好拆成独立段

如果未来又要恢复首页演示，建议把首页导航做成单独可切换的段，而不是和业务录制混在同一个脚本里。

这样可以在不同录制策略之间切换：

- 走首页演示版
- 走直达页面版

而不需要每次临时改脚本。

### 4. 上传文件最好预先做素材校验

当前上传文件靠 dry-run 文件检查已经够用，但如果后续要录更多业务视频，建议把“合同图片是否存在”和“是否被正确解析成绝对路径”单独做成一个显式前置校验输出。

### 5. 需要更多正式录制专用测试

这次的单测大多覆盖了浏览器动作规则，但还缺少一个“录制模式”级别的回归测试。

建议后续补：

- cursor overlay + recordVideo 下的首页点击
- 真实菜单 hover 后的稳定展开
- 远程搜索和收货地址异步加载
- 最终确认后页面回到列表页

## 结论

这次录制真正稳定下来的关键，不是再多加一个 workaround，而是把不稳定的首页导航拿掉，把所有容易歧义的选择器收紧，把 Element UI 的远程选择行为补齐。

最后结果是成功的，但后续如果要继续录类似业务页，最值得复用的是这几个原则：

1. 能直达页面就不要走首页。
2. 文本歧义高的地方尽量用 selector。
3. 远程选择和异步下拉要按真实控件行为写。
4. dry-run 通过后，还要再跑一次正式录制验证。
