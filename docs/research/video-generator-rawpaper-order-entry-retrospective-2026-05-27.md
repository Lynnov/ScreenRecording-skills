## 背景

本次目标是根据 `examples/video-generator/原纸贸易-订单录入.md` 录制一条原纸贸易订单录入教程视频，要求保留从首页进入工作台、找到原纸贸易模块、进入订单录入页面、填写订单并生成合同的完整演示路径。

## 用户补充的真实录制约束

本次复盘后，用户补充了几项关键事实，后续实现和录制流程必须以这些事实为准：

- 入口路径必须从首页开始演示，不能一开始直接打开订单录入详情页。
- 首页点击“开启工作”后，左侧菜单栏会展开并露出一级菜单。
- 鼠标 hover 某个一级菜单后，左侧菜单栏会延展出二级菜单。
- 本次流程应 hover “原纸贸易”，再点击二级菜单“订单录入”，进入订单录入详情页。
- 登录态可以继续用录制前导出 Playwright storage state 的方式保存。
- 用户原始脚本中的客户名称“测试”在业务系统里应当能触发下拉响应，下拉框选第一个；收货地址也选第一个。
- 如果流程涉及上传文件，用户可以提前把测试文件放到项目里，并在脚本中指定文件路径；本次合同文件是用户未补充的前置资料。
- 测试环境允许正常保存订单，保存副作用可接受。
- 成片时长应由润色后的脚本、实际旁白音频和 segment 时间轴自然计算，不能预设固定时长。
- 旁白应是简短操作加解释；某些显而易见的操作可以没有旁白，但时间轴也要正确保留空白或操作停顿。
- 原始用户脚本不应被直接覆盖。正确做法是保留原始脚本，复制一份润色稿，在润色稿中补充操作、旁白和可执行选择器。

## 主要问题

### 1. 最终音频被强行压缩，语速异常

`narration-raw.wav` 的时长约 98.8 秒，而两段手动录屏拼接后只有约 44.6 秒。合成时为了让音频匹配短视频，使用 `atempo` 把旁白压缩到 44 秒左右，压缩倍率约 2.22 倍。

这是错误处理。教程视频应以单句旁白时长驱动录制节奏，而不是录完短视频后再压缩旁白。正确结果应该是视频节奏跟着旁白走：每个操作后停留到对应旁白播放完成，字幕时间也跟同一个 segment 时间轴对齐。

### 2. 手动录制绕开了 pipeline 的 segment 时间轴

项目原生 pipeline 的正确路径是：

1. 解析脚本，得到 segment。
2. 为每个 segment 生成 TTS 音频，拿到实际音频时长。
3. 浏览器执行该 segment 的动作。
4. 根据 `actualAudioDurationMs + bufferMs` 等待，保证录屏片段覆盖旁白时长。
5. 用同一 timeline 生成字幕、合并旁白和渲染最终视频。

本次因为生成器在真实业务页的若干动作上失败，改用手写 Playwright 录制导航段和表单段。手动脚本只是用固定 `waitForTimeout` 控制节奏，没有读取每句旁白音频时长，也没有生成每个 segment 的 `videoStartMs` / `videoEndMs`。后续再人工生成字幕和音频时，就丢失了可信的时间轴。

### 3. 首页菜单交互理解不完整，hover 二级菜单没有被正确建模

从首页进入工作台的过程必须保留。用户补充后的真实路径是：点击“开启工作”展开左侧一级菜单，鼠标 hover “原纸贸易”，左侧菜单栏延展出二级菜单，再点击“订单录入”。

本次调试过程中，我把这段路径简化成了直接点击一级菜单或直接用详情页 URL，偏离了用户想要演示的真实操作。这说明脚本中的“hover 点击 左侧菜单栏”不是普通点击语义，而是一个明确的菜单交互模式：`click 开启工作 -> hover 一级菜单 -> click 二级菜单`。

实际调试还发现：

- 登录态导出成功后，首页可见“开启工作”。
- 原生 Playwright 可以点击或操作菜单进入“订单录入”。
- 生成器执行同类选择器时仍在 `seg-003` 超时。

后续应补充显式 `hover` 动作和左侧菜单二级展开的交互规则，而不是把导航段改成直达 URL。最终导航段用手动 Playwright 完成，但这也绕开了 pipeline 的时间轴。

### 4. Element UI 远程客户选择器不能用普通 fill

订单录入弹窗中的“客户名称”是 Element UI 的 remote `el-select`，初始 input 带 `readonly`。直接用生成器的 `fill` 或语义填充会失败，或者输入后不触发远程搜索。

实际可行的真实操作顺序是：

1. 点击客户名称选择框。
2. 等待 readonly 状态解除。
3. 执行全选快捷键。
4. 键盘输入客户关键字，例如“张晓东”。
5. 等待 `.cust-search-popper .el-select-dropdown__item` 出现。
6. 点击第一项。

这类控件需要生成器支持“remote select typing”交互模式，而不是简单的 `locator.fill()`。

### 5. 测试数据判断过早，且不应擅自改动用户给定数据

原脚本要求输入“测试”作为客户名称，并选择客户下拉框第一项；收货地址也选择第一项。用户补充说明：在业务系统中输入“测试”时，客户名称下拉框应当有响应。

本次调试中我没有稳定触发“测试”的下拉结果，就过早判断测试数据不可用，并把客户改成了“张晓东”。这是不合适的：用户给定的业务数据应先作为事实保留，失败时应继续排查控件交互方式、输入时机、接口响应和登录权限，而不是直接替换测试数据。

后续正确做法：保留原始脚本；复制一份润色稿；在润色稿中尽量不改变用户给定数据。只有在用户确认数据不可用，或明确允许替换时，才改用其他客户。

### 6. 上传文件是前置资料缺失，不是流程不可保存

表单段完成两条商品录入并点击“生成订单（合同）”后，系统弹出“生成订单(合同)”确认弹窗，要求上传线下合同文件。用户补充说明：如果流程涉及上传文件，可以提前把测试文件放到项目里，并在脚本中指定文件路径；本次是没有提前补充合同文件。

另外，测试环境允许正常保存订单，保存副作用可接受。因此不能把“无法最终确认”理解成业务上不能保存，而应记录为“缺少上传文件前置资料”。后续脚本应支持上传文件动作，并在录制包中声明合同文件路径。

### 7. 过度润色旁白和改写操作，偏离了用户原始脚本

本次我对脚本做了较大幅度的润色：添加了较多解释性旁白，修改了部分操作表达，还把用户给定的客户数据从“测试”改成“张晓东”。这带来两个问题：

- 旁白变长，导致原始 TTS 音频达到约 98.8 秒，远长于手动录屏时长。
- 操作被改写后，复盘和调试不再完全对应用户原始意图。

用户补充要求：旁白应简短，某些操作可以不配旁白，但时间轴也要正确留空；初始脚本不要直接改，应复制一份润色稿，在润色稿中补操作和旁白。

### 8. 调试产物和重复保存过多

本次产生了较多中间目录和失败产物，包括：

- `video-runs/原纸贸易-订单录入-audio-refresh/`
- `video-runs/原纸贸易-订单录入-导航段/`
- `video-runs/原纸贸易-订单录入-导航段-manual/`
- `video-runs/原纸贸易-订单录入-表单段/`
- `video-runs/原纸贸易-订单录入-表单段-manual/`
- `video-runs/原纸贸易-订单录入-final/`

大量中间产物让最终可交付文件不够清晰，也增加了误用错误 `final.mp4` 的风险。后续应该把一次任务的临时调试、最终素材、失败报告分层管理。

## 临时解决方式

本次为了尽快得到可查看素材，采取了以下临时方式：

- 使用可见 Chromium 导出 `intelligenttest-storage-state.json`。
- 使用手写 Playwright 录制导航段，保留首页到订单录入页面的业务路径，但没有完整模拟用户描述的 hover 展开二级菜单。
- 使用手写 Playwright 录制表单段，绕过生成器对 readonly remote select 的限制。
- 使用已有 TTS 音频、手工生成字幕和 ffmpeg 命令合成 `final.mp4`。
- 在调试中修改了用户原始脚本内容，没有先复制一份润色稿，这是流程问题。

其中最后一步把旁白压缩到录屏时长，是错误的临时处理。这个成片只能作为问题样例，不能作为正式交付视频。

## 正确修复方向

### 1. 拆段录制也必须保持 segment 时间轴

即使因为真实页面限制必须拆成导航段和表单段，也不能丢掉 timeline。正确做法是为每段脚本分别生成完整 timeline：

- 每个 segment 仍然有 `actualAudioDurationMs`。
- 手写 Playwright 每执行一个动作后，按该 segment 的目标时长等待。
- 录制输出记录每个 segment 在视频中的开始和结束时间。
- 最后拼接多个 timeline，并整体偏移后生成字幕和旁白。

### 2. 增加半自动录制接口

当前 pipeline 的 `recordTimelineSegments` 假设所有动作都由生成器自动执行。真实业务页经常需要手动或特殊动作。可以增加一个半自动 recorder：

- 输入仍是标准 timeline。
- 支持为某些 segment 提供 custom handler。
- handler 内可以用原生 Playwright 操作复杂控件。
- recorder 仍负责按旁白时长等待、记录 `videoStartMs` / `videoEndMs`。

这样既能处理复杂页面，又不会丢失音频和字幕时间轴。

### 3. 支持 hover 展开二级菜单

脚本语法需要明确支持 hover，而不是把 hover 隐含在“点击菜单”里。可以扩展为：

```markdown
点击 开启工作
悬停 原纸贸易
点击 订单录入
```

浏览器动作层应把 `悬停` 映射到 Playwright `locator.hover()`，并在 hover 后等待二级菜单容器出现。对于左侧菜单这种一级、二级菜单共用区域的页面，还需要在候选匹配时考虑菜单层级和当前 hover 状态。

### 4. 支持 Element UI remote select 交互

应在浏览器动作层增加一种专门的交互规则：

- 识别 `.el-select` + readonly input + remote popper。
- 点击输入框后等待 input 变为可编辑。
- 使用 keyboard 输入而不是 `fill()`。
- 支持 `Ctrl+A` / `Meta+A` 清空已有值。
- 等待指定 popper 中的选项出现。
- 点击匹配选项或第一项。

脚本语法可以扩展为类似：

```markdown
远程选择 客户名称 张晓东
选择 收货地址 第一个
```

### 5. 保护原始脚本，润色稿单独保存

后续处理用户脚本时，应采用三份文件策略：

- `原始脚本.md`：用户给定内容，不直接覆盖。
- `润色脚本.md`：补充旁白、拆分动作、修正错别字，但不擅自改变业务数据。
- `可执行脚本.md`：在润色稿基础上添加选择器、上传文件路径、特殊动作语法。

这样既能保留用户原始意图，也便于比较“润色改变了什么”。

### 6. 旁白应简短，并允许无旁白操作

本次旁白偏长，后续应控制旁白密度：

- 关键页面跳转、业务意义、保存副作用需要旁白。
- 连续字段输入可以合并成一句旁白。
- 很明确的点击、选择动作可以没有旁白。
- 无旁白 segment 仍应保留操作停顿或空白时间轴，不能因为没有旁白就让动作挤在一起。

### 7. 支持分段合成时按原始音频拉长视频

如果已经有手动录屏但视频短于旁白，不应压缩音频。更合理的兜底方式是：

- 保持原始旁白音频速度。
- 在每个 segment 的操作后冻结最后一帧或延长画面。
- 让视频时长匹配旁白，而不是让旁白匹配视频。

不过这仍是兜底，不如在录制时就按 segment 等待。

### 8. 明确业务数据前置条件

订单录入脚本应在开头或录制包中记录可用测试数据：

- 客户名称关键字，例如本次用户给定的“测试”。
- 下拉框选择策略，例如客户名称选第一项。
- 收货地址选择策略，例如收货地址选第一项。
- 是否需要合同文件。
- 如果需要最终保存，合同文件路径是什么。
- 是否允许真实保存。本次用户确认测试环境允许正常保存。

如果数据在录制时不可用，应优先排查交互和环境，而不是直接修改用户给定数据。

### 9. 产物目录规范化

建议一次真实业务录制统一输出到单个任务目录，例如：

```text

  screenshots/

```

临时失败产物可以放 `debug/attempt-001/`、`debug/attempt-002/`，避免散落多个同名目录。
